# Demo plan

Preflight: configure Supabase, run migration/seed, provision separate confirmed researcher/admin accounts, run docs/testing.md, and keep the main branch healthy. Every fictional record and test publication must display DEMO DATA. Prepare two signed-in browser profiles plus an anonymous profile. Never show credentials or the Auth dashboard on the projector.

Five-minute story:

1. Discover: homepage → research area → public publication. Point out the relationship to people and a project, and that login is unnecessary.
2. Understand: read the publication abstract and its purpose. Explain DEMO DATA honestly.
3. Participate: researcher signs in and submits a new demo title and abstract; show Submitted in the dashboard. The anonymous browser cannot see it yet.
4. Review: administrator opens the queue, starts review, then explicitly approves and publishes.
5. Public again: refresh the anonymous publication search and open the newly published output. Explain that the timestamp and publishing permission are database-enforced.

Use a unique demo title each rehearsal. Do not claim unsupported features work: interest capture, full entity detail modules, notifications and AI remain backlog. Keep backup screenshots or a local recording from an actually completed rehearsal; no simulated backend success. If the network fails, explain the outage and show prior captured evidence, clearly labelled.
